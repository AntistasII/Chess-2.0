# Архитектура Java-части

Код находится в `backend/src/main/java/chess/`. Общий движок (`ai`, `board`, `cards`, `pieces`, `game`, `opponent`, `serialization`, `config/GameProperties`) без изменений собирается и в Android-приложение через `android/prepare-build.py`. Остальные пакеты относятся только к серверу.

## Слои

```text
HTTP          server/ → controller/GameController → service/GameService (+ PlayerAccessService)
                                                        │
Сессия        game/GameSession ── OpponentTurn ── opponent/OpponentRegistry → Opponent
                 │          └──── SaveFile (путь: server.save-file)
Партия        game/Game ── TurnRules ── MoveRules ── pieces/Piece (ходы и атаки фигур)
                 │            └──────── CardRules ── cards/Card (цели и эффект карты)
                 └── GameOutcome, GameView (JSON для интерфейса), GameSave (файл сохранения)
ИИ            ai/Ai → TacticalHints (TacticalHint) → SearchEngine → PositionEvaluator
```

Зависимости направлены сверху вниз: правила не знают о сессии, сессия не знает об HTTP. ИИ и соперники работают только через публичные методы `Game` и копии позиции.

## Ядро партии

`Game` закрывает своё состояние и раскладывает его по частям с собственными правилами:

| Часть | Что хранит | Пример правила внутри |
|---|---|---|
| `Board` | фигуры, геометрия | расширение доски с переносом фигур |
| `CardPiles` | руки и их вместимость, колода, сброс | добор только при свободном месте, перемешивание сброса, маскирование чужих карт |
| `SquareEffects` | капканы, белые дыры | истечение срока, видимость невидимого капкана |
| `CastlingRights` | сохранённые права рокировки | потеря права после хода короля или ладьи |
| `GameSettings` | режим, лимит руки, сложность | проверка допустимых значений |

Очередь хода, счётчики, итог (`GameResult`), версия и снимок для «Отмены хода» — поля самой партии. Классы правил (`TurnRules`, `MoveRules`, `CardRules`, `GameOutcome`) не хранят состояния. Они создаются на одну операцию и меняют партию через методы видимости пакета.

### Типы вместо строк

| Тип | Внешнее значение (`id()` / `code()`) |
|---|---|
| `GameMode` | `ai`, `human`, `chatgpt`, `network` |
| `Difficulty` | `easy`, `normal`, `hard` |
| `GameResult` | `""`, `white`, `black`, `stalemate`, `whiteResigned`, … |
| `ActionKind` | `move`, `card`, `draw` |
| `PieceType` | `P`, `N`, `B`, `R`, `Q`, `K` |

Строки остаются только на границах: в YAML, HTTP-запросах, JSON состояния и файлах сохранения. Внутри движка значения перечислений сравниваются напрямую, а `Action` отвечает на `isMove()`, `isCard()`, `isDraw()`, `isCastling()` и `promotion()`.

Цвет стороны везде обозначается как `boolean white`, как в фигурах и ИИ. Отдельного перечисления нет: оно добавило бы преобразования на самых частых путях поиска.

## Как проходит одно действие

1. `GameService` проверяет доступ, версию и очередь и вызывает `GameSession.play(version, actionId)`.
2. `Game.play` находит действие среди `legalActions()`. Каждое кандидатное действие (`TurnRules.candidateActions`) уже проверено на копии позиции: собственный король не остаётся под шахом.
3. `TurnRules.applyUnchecked` исполняет действие: обычный ход отдаётся `MoveRules`, карта — `CardRules` (её эффект реализует сам класс карты), добор — `CardPiles`. Затем срабатывают капканы, и `Game.advanceTurn()` передаёт очередь и снимает истёкшие эффекты.
4. `Game` записывает историю и повторение позиции, а `GameOutcome` определяет мат, пат и автоматические ничьи.
5. `GameView` возвращает интерфейсу новое состояние.

Ход автоматического соперника идёт так же, но расчёт выполняется без блокировки. `OpponentTurn.observation` готовит копию, на которой рука соперника, колода и невидимые капканы скрыты. Затем `Opponent.choose` выбирает действие, а `OpponentTurn.apply` применяет его, только если версия партии не изменилась.

## Как расширять

**Новая карта.** Добавьте значение в `CardType` и класс с `@CardDefinition` в `cards/impl` (см. [CARDS.md](CARDS.md)). Реестр, колоду и сохранения править не нужно. Если карта должна учитываться в спокойном поиске ИИ (возвращает материал), добавьте её тип в `SearchEngine.tactical`; ценность карты в руке задаётся в `PositionEvaluator`.

**Новый вид соперника.** Унаследуйте `Opponent` (режим, `automatic()`, `choose`) и зарегистрируйте его в `OpponentRegistry.register`. Если для него нужен новый режим партии, добавьте значение в `GameMode` и секцию `chess.game.opponents.<id>` в `application.yml`: список допустимых ключей настроек строится по самому перечислению.

**Новый итог партии.** Добавьте значение в `GameResult` со строковым `id` для интерфейса и установите его в `GameOutcome`.

**Новая фигура.** Добавьте значение в `PieceType` с однобуквенным кодом и класс-наследник `Piece` (или `SlidingPiece`), затем ветку в `PieceFactory`. Компилятор укажет `switch` без ветки `default` (фабрика, клетки возрождения); стоимость фигуры для ИИ задайте в `PositionEvaluator.materialValue`.

**Другой путь сохранения.** Задайте `server.save-file` в `application.yml` или переменную окружения `SERVER_SAVE_FILE`.

## Совместимость

Формат файла сохранения (`format: 1`), JSON состояния и строковые ключи повторения позиции при рефакторинге не менялись. Это проверено так: старая и новая версии сыграли одни и те же партии из одного сохранения, и после каждого из 2350 действий (из них 297 розыгрышей карт двадцати типов) их сохранения совпали поле в поле; JSON состояния для белых и чёрных совпал на 600 снимках. Карты со случайным выбором («Обмен планами», «Уничтожить карту») и перемешивание сброса в этой проверке исключены: они дают разные результаты даже при двух запусках одной версии.

Позже в сохранение добавлено необязательное поле `handLimits` (вместимость рук белых и чёрных). Файлы без него загружаются с начальным лимитом из `settings`; ключ повторения позиции дополняется `|limits:…` только при изменённой вместимости, поэтому ключи старых сохранений не меняются.

## Известные ограничения

Клетки возрождения (`Game.startingSquares`) и рокировки рассчитаны на стандартную расстановку RNBQKBNR, даже если в `chess.game.back-rank` задан другой порядок. Учёт произвольной расстановки потребует хранить её в партии и в сохранении.
